# Database Rules (ACID + Prisma + PostgreSQL)

## ACID Properties

### Atomicity
- **Operations that must succeed or fail together go in a Prisma `$transaction`.**
  - Example: creating an application + its default EHR access = one transaction.
  - Example: approving a user + granting default app access = one transaction.
- For Redis operations that must be atomic, use Lua scripts (e.g., `INCR + EXPIRE` in `cache.incr()`).
- Never split related DB writes across separate `await` calls without a transaction.
- Use `cache.getdel()` for atomic read-and-delete (e.g., refresh token consumption).

### Consistency
- **All constraints must be enforced at the schema level**, not just application code:
  - `@unique` for business uniqueness (email, clientId, [appId + ehrName])
  - `@relation(onDelete: Cascade)` for parent-child cleanup
  - Enums for constrained values (`AppType`, `OrgRole`, `UserStatus`)
  - `@@unique([applicationId, ruleType])` for composite uniqueness
- Prisma schema is the single source of truth for data structure. If a constraint isn't in the schema, it doesn't exist.
- Validate data before write (DTOs/Zod), but rely on schema for enforcement.

### Isolation
- **Tenant isolation is mandatory.** Every query that touches user data MUST include `organizationId` in the WHERE clause.
- Use `findFirst` + `update` for single-record mutations (not `updateMany` which skips Prisma extensions and doesn't return the updated record).
- For distributed locks (token refresh), use `cache.setNx()` with TTL to prevent deadlocks.
- Never trust client-provided IDs alone — always join with org context.

### Durability
- **Critical state** (users, apps, configs, rules) lives in PostgreSQL — never only in Redis.
- **Ephemeral state** (connections, sessions, SMART state, cache) lives in Redis with TTL.
- **Secrets** live in Doppler/AWS Secrets Manager — never in DB, never in committed files.
- PostgreSQL is hosted on Aiven with automated backups — no manual backup management needed.

## Query Rules

### Indexing
- **Every `findMany` must have an index.** Check `@@index` in schema before adding new queries.
- Current indexes:
  ```prisma
  User         @@index([organizationId])
  Application  @@index([organizationId])
  AppEhrAccess @@index([applicationId])
  UserAppAccess @@index([userId])
  CdsRule      @@index([applicationId])
  ```
- Before adding a new `where` clause pattern in a query, verify an index exists.

### Select & Include
- **Never `SELECT *` in production queries.** Use Prisma `select` to fetch only needed fields for list endpoints.
- Use Prisma `include` for related data fetching — prevents N+1 queries.
- For composite endpoints, use a single query with `include` rather than multiple separate queries.

### Pagination
- **Paginate all list endpoints.** Use `take`/`skip` or cursor-based pagination.
- Default page size: 50, max: 200.
- Always return total count alongside paginated results for UI pagination controls.

### Query Safety
- **No N+1 queries.** Use Prisma `include` for related data, or batch with `Promise.all`.
- **No raw SQL** unless Prisma can't express the query. Document why if used.
- **No `deleteMany` without confirmation** — prefer soft delete (status change) for user-facing data.
- Use `updateMany` only for batch operations where you don't need the result. For single-record updates, use `findFirst` + `update`.

## Prisma Schema Rules

### Naming
- Models: `PascalCase` (e.g., `Application`, `AppEhrAccess`)
- Fields: `camelCase` (e.g., `clientId`, `organizationId`)
- Database columns: `snake_case` via `@map("column_name")`
- Database tables: `snake_case` via `@@map("table_name")`
- Relations: named after the target model (e.g., `application Application`)

### Field Standards
- IDs: `@id @default(uuid()) @db.Uuid` — UUIDv7 generated by application for `CoreEhrConnection`, default UUID for others.
- Timestamps: `createdAt DateTime @default(now())`, `updatedAt DateTime @updatedAt`
- Soft delete: use `status` enum field, not a `deletedAt` timestamp.
- JSON fields: use `Json` type for flexible config (e.g., `cdsConfig`, `ehrConfig`). Document expected shape in comments.

### Migrations
- Use `prisma db push` for development iteration.
- Use `prisma migrate dev` for production-ready migrations.
- Every migration must be reversible or documented as breaking.
- Never modify a production migration file after it's been applied.
- Test migrations against a copy of production data before deploying.

## Anti-Patterns

| Anti-pattern | Correct Approach |
|-------------|-----------------|
| `updateMany` for single record | `findFirst` + `update` |
| Query without `organizationId` | Always scope by tenant |
| `findMany` without index | Add `@@index` first |
| Storing secrets in DB | Use Doppler/AWS Secrets Manager |
| Storing sessions in DB | Use Redis with TTL |
| Raw SQL for simple queries | Use Prisma client |
| Missing `onDelete: Cascade` | Add to schema for parent-child relations |
